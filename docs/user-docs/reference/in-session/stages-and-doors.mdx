# Stages and doors

A **stage** names a workflow posture and its read-only or read-write mode. A **door** is a way to
enter that stage or drive its operation. Four related facts must stay separate:

- A **registry warm door** says the stage can be driven from an existing Pi session while keeping
  that session's run id.
- A **standalone slash command** is a human-typed launcher registered by the extension. A
  warm-capable stage does not necessarily have one.
- A **cold-local launcher** starts a fresh local session through the perk CLI and mints a run id.
- **Cold-remote eligibility** allows the remote runner to dispatch the bounded stage. It is not a
  synonym for having a cold-local launcher.

That distinction matters for `gist-author` and `objective-author`, which are warm-capable but have
no standalone slash launcher. It also matters for `implement`: registered `/implement` refreshes
context only inside an existing implement worktree and does not make the stage warm-enterable.

## Notable cases

- `gist-author` and `objective-author` can participate in warm authoring flows, but neither has a
  `/gist-author` or `/objective-author` command. Their direct launchers are cold.
- `/implement` is an in-worktree context refresh. Fresh or cross-worktree implementation starts
  with `perk implement`.
- `address` is the only stage available through all three door classes.
- Cold-remote dispatch is deliberately limited to the bounded `implement` and `address` stages.
- `audit` is an isolated, dev-only read-only stage reached through `perk-dev`, not the operator
  `perk` CLI.
