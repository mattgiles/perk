# Docs-site visual & authoring blueprint

This is the **binding visual and authoring blueprint** for perk's local Starlight documentation
site (Objective #1622, node 1.3). It converts the field-guide/instrument-panel direction into a
complete token system, type system, composition set, diagram language, responsive contract, and
component-override budget. The decisions were verified in a disposable scaffold against the
already-selected `astro@7.2.1` + `@astrojs/starlight@0.41.7` bridge; no site shell or operator
content lands with this record.

## §1 Binding scope

### What this blueprint binds

Later plans treat the following as decided input, not as open visual-design questions:

- the two intentional theme palettes, their Starlight mappings, perk-owned tokens, and semantic
  status colors (§2);
- local Inter Variable + IBM Plex Mono, exact package pins, type scale, measure, and fallback
  posture (§3);
- the home, quadrant-landing, and reference compositions in both themes, including their narrow
  linearization (§4);
- the five-diagram shared legend and its two rendering contracts — static SVG and
  interactive semantic HTML (§5);
- responsive, zoom, overflow, and reduced-motion behavior (§6);
- a zero-entry component-override set under an absolute cap of three (§7);
- the result of the content/IA route-detail reconciliation (§8);
- the article-page and shell-chrome finish treatments (§11).

The named consumers are node 2.1 (shell `customCss` wiring and Fontsource vendoring), node 2.4
(baseline rendering), node 3.1 (home and landing execution plus the first diagrams), nodes 4.1–4.5
(reference and explanation families), node 5.1 (visual/accessibility hardening), and node 5.2 (the
final gate).

**Reconciliation rule:** changing a bound decision in this record requires an explicit objective
reconciliation on **Objective #1898** (the reconciliation authority for this record, transferred
from closed Objective #1622 by this amendment). This includes changing either font family, a final token,
composition order, diagram semantics, the committed override set, or the absolute override cap.
Ordinary implementation that applies these decisions does not require reconciliation.

### Relationship to the sibling records

- [`docs-site-blueprint.md`](./docs-site-blueprint.md) remains authoritative for reader IA, routes,
  sidebar ownership/order, the five `replace` dispositions, migration intent, and acceptance
  matrices. Visual treatment may not alter those decisions.
- [`docs-site-bridge-spike.md`](./docs-site-bridge-spike.md) remains authoritative for the external
  content-tree bridge and exact Astro/Starlight pair. This record uses that bridge without
  re-selecting it.

### Out of scope

No site shell, bridge implementation, operator-content edit, font binary, landing page, diagram,
component override, screenshot, deployment surface, or repository build-command implementation
is committed here. Nodes 2.1 onward execute the blueprint. The evidence scaffold and all simulated content are disposable
(§10).

The themes are designed separately rather than generated by inversion. Light mode is warm paper
plus a white raised surface; dark mode is green-black plus a slightly lifted green surface. Large
areas remain neutral. Accent is reserved for links, current state, focus, and primary action.

## §3 Typography and the font decision

### Selected local fonts

The selected pair is **Inter Variable for UI/prose** and **IBM Plex Mono for code and operational
labels**. Node 2.1 records these exact dev-dependencies in `docs/site/package.json` and its npm
lock:

```json
{
  "devDependencies": {
    "@fontsource-variable/inter": "5.3.0",
    "@fontsource/ibm-plex-mono": "5.3.0"
  }
}
```

Registry queries at execution returned `5.3.0` for both packages; those exact values, not ranges,
are bound above. Both packages report `OFL-1.1` and ship their license inside the package. No font
binary is checked into git. The site imports Inter's normal variable CSS and IBM Plex Mono's Latin
400/500/600 CSS through Starlight `customCss`:

```js
customCss: [
  '@fontsource-variable/inter/index.css',
  '@fontsource/ibm-plex-mono/latin-400.css',
  '@fontsource/ibm-plex-mono/latin-500.css',
  '@fontsource/ibm-plex-mono/latin-600.css',
  './src/styles/tokens.css',
]
```

The token CSS then applies:

```css
:root {
  --sl-font: 'Inter Variable';
  --sl-font-mono: 'IBM Plex Mono';
}
```

IBM Plex Mono applies to fenced/inline code, terminal and path labels, diagram operational labels,
spine stages, short eyebrow labels, and compact status labels. It does not replace prose.

The scaffold emitted 13 local font assets totaling 320 KiB and increased total static output by
324 KiB. Installation added 4,048 KiB under `node_modules`; a warmed selected-font build measured
3.82s wall versus the sibling spike's 4.4s warm baseline. This is not material build-weight or
rendering harm, so the local-font decision survives (§9).

### Documented fallback, not selected

If a future measured regression demonstrates material weight or rendering harm, objective
reconciliation may replace the custom pair with these tuned stacks — never a remote font request:

```css
--sl-font: -apple-system, BlinkMacSystemFont, 'Segoe UI Variable', 'Segoe UI', Roboto,
  'Helvetica Neue', Arial, sans-serif;
--sl-font-mono: ui-monospace, SFMono-Regular, Menlo, Monaco, Consolas, 'Liberation Mono',
  'Courier New', monospace;
```

Normal browser fallback after an individual local font fails to load may use the same stack; that
does not change the selected design.

## §5 Diagram legend

The required five-diagram family — the core flow (the workflow spine with its review loops,
satellite flows, and the docs/learned cache), plans inside objectives, two planes/one
contract, warm/cold doors, and headless/remote flow — shares this vocabulary.

### Semantic vocabulary

| Meaning | Shape/glyph | Line/style | Color token | Required text encoding |
|---|---|---|---|---|
| Ordinary stage/node | 6px rounded rectangle, leading `○` | solid 1px | text + border | stage name |
| Current node | same rectangle, leading `▸` | solid 2px | accent/strong | `current` in accessible text |
| Completed node | same rectangle, leading `✓` | solid 1px | success | `complete` in accessible text |
| Conditional step | diamond `◇` beside stage | dashed incoming arrow | warning or muted | `(if …)` condition beside label |
| Human gate | double-outline rounded rectangle, `!` | solid incoming; no automatic outgoing implication | warning | explicit `HUMAN GATE` + action |
| Plane/ownership region | 10px rounded container | solid boundary | surface + border | region heading (`Exterior`, `Interior`) |
| Trust/process boundary | rectangular region | dashed boundary | canvas + border | boundary label on the line |
| Durable state/artifact | document cylinder/tab shape | solid | accent-low + border | artifact/state noun |
| Review loop | `↻` prefix on a text badge | none (text row) | muted | participants named in the label (`human review`, `PR review`, `optional agent wave`) |
| Expandable satellite region | native `<details>` container, card radius (10px), `<summary>` disclosure marker | solid 1px border | surface + border | summary label + collapsed-visible hint; content complete when expanded/no-JS/print |
| Durable-cache loop | loop badge on the §5 durable-state cylinder (CSS-shaped) | solid | accent-low + border | `↻ <name> → <consumer>` (or an em-dash qualifier) |
| Labeled feed | `⇢` glyph / dashed rule | dashed | muted | mandatory label naming source ⇢ target + the exchanged context; a mediated feed names every hop |

Color may reinforce these meanings but never creates them. A monochrome rendering must still
preserve node state, conditionality, gates, boundaries, and direction through glyph, shape, line
style, and label.

### Arrow semantics

- solid single arrow: ordered control or state transition;
- dashed single arrow: conditional transition **or** labeled feed — a label is mandatory
  either way (the adjacent condition for a conditional transition; source ⇢ target + the
  exchanged context for a feed);
- solid bidirectional arrow: explicit read/write exchange, labeled with the exchanged artifact;
- no arrowhead: grouping/association only;
- crossing a dashed trust/process boundary requires a label at the crossing.

Avoid decorative loops, perspective, or animated flow. When a diagram needs a legend beyond this
shared vocabulary, simplify it rather than inventing a one-off visual language.

### Typography and color

Operational labels use IBM Plex Mono 500; explanatory annotations use Inter. SVG labels are at
least 16 CSS px at their final 100% size so they remain legible at 200% zoom. Canvas, surface,
text, muted, accent, status, and border colors come only from §2 CSS properties — never literal
light/dark hex values inside a diagram.

### Rendering and accessibility contracts

The family renders through two contract classes. Requirements shared by both: labels ≥ 16 CSS
px at final 100% size, colors only from §2 CSS properties, meaningful source order, an
**adjacent textual equivalent** immediately before or after the figure (one sentence
introducing the question, then a short sequence/relationship statement containing every node
and edge a reader needs to act on), no page-level horizontal overflow at any width, and 320px
linearization (scale without shrinking labels below the floor, or switch to a stacked vertical
arrangement with the same reading order). At 200% zoom, labels do not overlap or clip; a
complex diagram may scroll in an explicitly labeled contained region.

**Static-SVG contract** (members: the two-planes, plans-inside-objectives, warm/cold-doors,
and headless/remote components). Diagrams are theme-aware inline SVG; their CSS consumes
`--perk-*` custom properties, so one SVG serves both themes. Every semantic diagram has:

1. `role="img"` plus an SVG `<title>` and `<desc>` associated through `aria-labelledby` (or
   equivalent accessible naming when rendered through a component);
2. meaningful groups and labels in source order;
3. the adjacent textual equivalent above;
4. no essential hover-only detail.

**Interactive semantic-HTML contract** (member: the core-flow component). Real HTML carries
all content — every node, loop, feed, and condition is source-order text in semantic elements;
connectors are decorative CSS-generated glyphs/rules in the accessibility-neutral
`content: "…" / ""` form (decorative SVG is permitted by this contract class but unused — the
core-flow component pins zero SVG). Expandable regions are independent native
`details`/`summary` disclosures, **source-expanded**: the unenhanced page (no-JS, print, the
static a11y gate) is content-complete; enhancement collapses them by default, and
`beforeprint` re-expands (with `afterprint` restore). Layout is container-keyed — never a
viewport media query: the shared figure container drives the bound 640px (horizontal spine)
and 960px (satellite row) thresholds, and each satellite card is additionally its own named
inline-size container (`satellite`) whose summary hint flips inline↔stacked on the card's
own width at one intentional threshold (440px). Supplementary tooltips are the sanctioned refinement of “no
essential hover-only detail” (still governing — tooltip copy is supplementary color only,
never load-bearing): triggers are real `<button type="button">` elements with
`aria-describedby` always pointing at the colocated tooltip; per trigger, hover/focus/pin
intents and a dismissal latch drive visibility — visible ⇔ (hover ∨ focus ∨ pinned) ∧
¬dismissed — so hover/focus show, losing one intent while another holds does not hide,
blur/pointerleave hide once intents drop, tap toggles a pin on hover-incapable devices
(focus/pointer are not intents there), document-level Escape dismisses and latches until
intent fully drops or a new tap, and only one tooltip is visible at a time. The visible
tooltip is itself **hoverable** (WCAG 2.2 SC 1.4.13): it holds the same hover intent as its
trigger and a hit-area bridge spans the trigger–tooltip gap, so the pointer can cross onto
the tooltip without dismissing it. Keyboard
operability, visible focus, and reduced-motion behavior follow §2/§6.

The authoring tool is deliberately unbound until node 3.1 planning. Hand-authored SVG/HTML, a
script, or another tool is acceptable only when its output conforms to its rendering contract.

## §6 Responsive behavior

The acceptance widths are **320, 768, 1280, and wide (1600px in the scaffold)**. These are review
points, not permission to create four unrelated layouts.

| Surface | 320px | 768px | 1280px | Wide |
|---|---|---|---|---|
| Starlight shell | Native mobile header/menu | Native compact shell | Left sidebar + center + right TOC where applicable | Same shell; center does not stretch prose |
| Home | One reading column; spine/diagram stack | One or two columns where each card remains useful | Composition in §4A | Same max-width composition, more outer whitespace |
| Quadrant landing | One card/link per row | Recommended cards may be 2-up | 2–3 recommended cards + grouped lists | Same max-width composition |
| Reference | Collapsed page TOC; contained table/code scroll | TOC follows Starlight breakpoint | Right TOC; dense child may use 92ch mode | No uncapped table/page growth |
| Diagram | Vertical/contained | Fit or stack by content | Preferred horizontal composition | Centered; labels retain size |

Specific invariants:

- Cards and split regions linearize in source/reading order; no action or information depends on
  hover or column position.
- Code blocks scroll horizontally inside titled Expressive Code frames. Do not force-wrap shell
  commands, paths, or output where wrapping changes meaning.
- Wide tables scroll inside an obvious bordered region. No `table`, `pre`, SVG, or spine strip may
  widen the page.
- Mobile header, menu, search, and navigation remain Starlight-native. A visual preference is not
  a reason to override them.
- A 200% browser zoom at a 1280px physical viewport is treated as an approximately 640px CSS
  viewport: all functions remain present, source order remains correct, and no page overflow is
  introduced.
- The spine never auto-plays. Theme/navigation transitions are optional and minimal.
  `prefers-reduced-motion: reduce` disables nonessential animation and collapses transition
  durations to effectively zero.
- Visible focus, skip navigation, landmarks, heading order, and accessible names inherited from
  Starlight are preserved.
